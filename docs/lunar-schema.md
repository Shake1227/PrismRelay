# Verified Lunar configuration schema

Prism Relay 1.0.0 inspected the key names and JSON types of locally installed Lunar game settings on 2026-09-30. The inspection was read-only. No account or authentication files were opened. No real values were copied into this repository, fixtures, logs, or share codes.

The verified layout is `.lunarclient/settings/game/<profile>/`, containing `mods.json`, `general.json`, `controls.json`, and `performance.json`. Those profiles are Lunar GUI presets. The Minecraft game destination is the OS default game directory, or the one game directory explicitly chosen in Settings. It is not selected through launch configurations.

In 1.0.2, scanning exposes one Minecraft game destination. Windows uses `%APPDATA%/.minecraft`; macOS uses `~/Library/Application Support/minecraft`. Alternate version folders and Lunar isolated profiles are not scanned as game destinations. A custom game directory can be specified in Settings. This avoids applying a code to an unused version folder.

When the chosen game directory contains `optionsLC.txt`, its flat JSON string settings and the adjacent `options.txt` belong to that same destination. Import updates selected keys present in each file within a single backup transaction, preferring the LC value for export. Regular-options-only keys are not invented in LC. A damaged or unsupported existing LC file blocks that destination's game settings.

LC stores FOV as a degree string from 30 to 110; Minecraft's regular options file stores the normalized ratio from -1 to 1. Their relationship is `degree = 70 + 40 * ratio`. This conversion and the string-reading behavior were checked against the installed Minecraft 1.21.11 and Lunar game code. Shared codes continue to use the existing Minecraft options string schema. LC values with other JSON types or values outside approved grammars remain read-only. JSON token updates preserve unknown fields, precision, whitespace, and byte order marks.

`mods.json` has an object root. Its module objects use names such as `FPS`, `CPS`, `COORDINATES`, `KEYSTROKES`, and `ARMORSTATUS`. HUD children can be nested inside a module. Observed leaves include boolean `enabled`, numeric `x` and `y`, string `position`, and nested `options`. Options can contain booleans, numeric strings, keybind strings, and color objects with numeric `value` and boolean `chroma` fields. Root `version`, module `panelIndex`, `seen`, and `lastModified` fields are metadata and are excluded from sharing.

`general.json` and `controls.json` have object roots. Confirmed general settings include appearance booleans and a `backgroundColor` object. Confirmed controls include keybind strings and separate modifier booleans. Some profiles contain only a schema version or an empty object. `performance.json` was observed with an object root and string enum fields whose semantics were not verified; it remains outside the initial schema.

[src-tauri/src/lunar_schema.json](../src-tauri/src/lunar_schema.json) is the closed allowlist of observed, approved paths and their scalar types. It contains key names and type descriptions only. Before 1.0.4, export enumerated keys actually present in each file. A known module whose root `enabled` boolean is explicitly shared can be updated even when that leaf is absent in the destination, provided the module object exists. Before 1.0.4, the module-specific factory default was not inferred for export. Newly introduced keys remain untouched until their schema and privacy properties are reviewed.

Strings use bounded grammars. Position strings are accepted only when they match a closed direction vocabulary after case and separator normalization. Of the inspected position fields, 102 matched this grammar and 19 did not; the latter remain read-only. Numeric option strings must parse as bounded finite numbers. Keybind strings must identify a recognized keyboard or mouse key. Free text, unknown enums, custom crosshair payloads, macro actions, account fields, server addresses, waypoint coordinates and payloads, Quickplay data, and unknown arrays are excluded.

## HUD layout adaptation in 1.0.3

Read-only inspection of the installed Lunar 1.21.11 game code established that the common HUD root stores anchor-relative offsets in `x` and `y`. Rendering divides these offsets by the component scale and adds the anchor origin. The ten verified anchors are `topLeft`, `topCenter`, `topRight`, `middleLeft`, `middleCenter`, `middleRight`, `bottomLeft`, `bottomCenterLeft`, `bottomCenterRight`, and `bottomRight`.

The effective HUD viewport is the physical game client area divided by Lunar's global HUD coordinate factor. That factor includes Minecraft GUI scale, its Unicode-font adjustment, Lunar's `useMinecraftScale` and `highDPIScale`, and the Mac framebuffer-to-logical-height ratio. The implementation mirrors the inspected integer truncation and Java float calculations. Confirmed factory defaults are GUI scale 0, Unicode font false, Lunar scale mode `auto`, and high-DPI scaling true. Ambiguous or unsupported saved values make automatic adaptation unavailable. Automatic adaptation also requires `optionsLC.txt` with an exact, known modern Lunar `lastLaunchedVersion` ID. This local ID is a value such as `v1_21_11`, written by Lunar itself, and selects the modern renderer calculation. The frozen accepted IDs are in `hud.rs`. Missing, unknown, and legacy IDs make adaptation unavailable; installed version directories are not used to infer the renderer. Legacy font and coordinate behavior remains outside the verified automatic path, and exact-value import remains available.

Exports containing verified root coordinates with an available source viewport use PRS3 and store one effective HUD viewport. If source measurement or renderer settings are unavailable, export retains PRS2 exact-value sharing; import requires explicit preservation for those root coordinates. Import transforms `x` by the target/source viewport-width ratio and `y` by the height ratio. When GUI scale settings are also selected and applicable to the Minecraft destination, the target viewport uses their prospective values. Anchors, component scale, child coordinates, and other settings retain their original values. Multiple source HUD profiles cannot share one viewport.

The closed root-module list is `ARMORSTATUS`, `BOSSBAR`, `CLOCK`, `COMBO`, `COOLDOWNS`, `COORDINATES`, `CPS`, `DIRECTION_HUD`, `FPS`, `ITEM_COUNTER`, `ITEM_TRACKER`, `KEYSTROKES`, `MEMORY`, `MOMENTUM`, `PING`, `PLAYTIME`, `POTION_EFFECTS`, `REACH_DISPLAY`, and `STOPWATCH`. Unverified coordinate semantics remain unchanged.

The size model is the standard decorated game window maximized on Prism Relay's current monitor. Windows measures an application-owned, invisible maximized window's client area; Mac converts the screen's visible frame through AppKit's standard window content-rectangle calculation. Taskbars, Dock, menu bar and title bar are excluded. This follows the native window styles in [GLFW's Windows implementation](https://github.com/glfw/glfw/blob/3.4/src/win32_window.c) and [Mac implementation](https://github.com/glfw/glfw/blob/3.4/src/cocoa_window.m). Physical framebuffer and logical window coordinates are distinct, as described in the [GLFW window guide](https://www.glfw.org/docs/3.4/window_guide.html#window_fbsize).

The import preview displays the resolved physical client size and adjusted values. Its fingerprint includes the resolved viewport and prospective values, so moving to another monitor, changing display scale or relevant saved GUI settings requires a new preview. Users can preserve exact offsets or provide bounded physical client dimensions manually. PRS1 and PRS2 remain readable, but have no source viewport and require regeneration or explicit preservation for these coordinates.

The Lunar parser rejects duplicate JSON keys, damaged JSON, excessive arrays or objects, and oversized files. Import merges verified scalar paths in the destination, including the approved sparse insertions described below. The current primary registry takes precedence over the older observed allowlist. Primary Float/Int options require JSON numbers within their approved ranges. A saved value with an incompatible type or range is skipped; its factory default does not mask that mismatch. Older paths outside the primary registry retain their individually approved scalar types. Legacy share codes can still use the older approved grammar. Import converts inspected legacy numeric-string fields to current JSON numbers only when conversion is lossless and the current bounds are satisfied. Unverified conversions from numeric strings to current enums are skipped and reported in preview. Current exports continue to use the primary types. It patches only the selected scalar tokens in the original JSON text. Unknown values, numeric precision, field ordering, escaping, and whitespace are preserved byte-for-byte. Files and traversed directories that are symlinks are denied. These guarantees do not make this an official Lunar integration: future Lunar releases can change the schema, and unsupported fields intentionally remain read-only.

The active Lunar GUI preset is read locally from `profile_manager.json`. Its `name` must match a discovered preset directory exactly, and exactly one entry must have `active=true`. Server, display-name, icon, and other manager fields are excluded from settings and share codes. The GUI uses this preset as the initial choice while retaining a valid explicit user choice.


## Public MOD options and appearance in 1.0.4

[src-tauri/src/lunar_appearance.json](../src-tauri/src/lunar_appearance.json) records the additional public scalar settings checked against the installed Lunar 1.21.11 game code. Each entry identifies its file, exact pointer, owning component, scalar kind, role, and any approved factory default, numeric bounds, or enum vocabulary. This is a separate closed registry; arbitrary option names and free-text values are not accepted.

The registry covers verified public MOD options and appearance controls: toggles, display modes, key settings, packed colors, rainbow effects, component scale, and numeric box dimensions or spacing. A confirmed default is added to the scanned settings when its owning MOD or HUD child exists and the leaf is absent. Unconfirmed defaults are never inferred. If a known parent exists with an unexpected JSON type, that field remains unavailable rather than being replaced.

Import can add a selected approved leaf and its missing option/color containers beneath an existing component. It does not create an absent MOD or HUD child. Existing unselected leaves and unknown data keep their original bytes. Sparse additions are included in the same preview fingerprint, backup, validation, and atomic write transaction as other selected settings. Enum values and numeric bounds come from the registry, and incompatible destination types block the affected field.

Verified color objects store `value` as a signed 32-bit ARGB integer: the upper eight bits contain opacity and the lower twenty-four bits contain RGB. The UI displays a color sample, RGB hex value, and opacity percentage; the share code and import still use the original integer. Independent `chroma`, `chromaSpeed`, and `chromaType` leaves control rainbow coloring, its speed, and its wave or hue-shift mode. Other integers are displayed as ordinary settings rather than being guessed to be colors. Primary scale, width, height, and padding fields use validated JSON numbers. Older allowlisted fields retain their separately approved scalar representations.

This registry applies to the verified Lunar format, not every future Lunar version. Private or unverified content, including macro bodies, waypoint coordinates, account identifiers, server addresses, and custom payloads, stays outside sharing. HUD coordinate adaptation from 1.0.3 remains separate and changes only the previously verified root X/Y coordinates.
